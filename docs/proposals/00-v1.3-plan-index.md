# RoyaScaff v1.3 Plan Index

> **Status:** Proposed implementation plan — awaiting owner approval.  
> **Current engine:** v1.2.5.  
> **Target release:** v1.3.0.  
> **Implementation boundary:** These files plan the work only. No active file under `engine/`, `skills/`, `bin/`, or `package.json` is changed by this plan.

## Executive decision

RoyaScaff v1.3 should evolve from a Markdown workflow collection into a **Markdown-first software-development knowledge compiler**.

The engine will continue to produce readable Markdown, but critical metadata, relationships, lifecycle transitions, context selection, and validation will become structured and deterministic.

```text
Developer intent
    ↓
Canonical knowledge repository + artifact graph
    ↓
Impact resolver
    ↓
Context compiler
    ↓
Composable workflow skills
    ↓
Approved execution plan
    ↓
Implementation
    ↓
Deterministic validation + semantic review
    ↓
Canonical knowledge reconciliation
```

## The central architecture decision

v1.2 mixes two different dimensions. v1.3 separates them:

| Dimension | Purpose | Examples |
|-----------|---------|----------|
| **Knowledge layer** | What the system knows | requirements, architecture, domain, workflows, contracts, data, implementation map, decisions |
| **Scope and lifecycle** | Why a subset is being viewed or changed | canonical current state, change delta, execution plan, generated context slice, historical record |

A feature slice therefore does not own duplicate requirements, architecture, and contracts. It is a reference-based selection across the canonical knowledge layers.

## Decisions made by this plan

These are recommendations, not unresolved alternatives:

1. Keep `project/` as the generated system-knowledge root for compatibility.
2. Redefine “Main Blueprint” as `project/system-map.md` plus the canonical knowledge tree, not one giant document.
3. Redefine “Slice Blueprint” as a generated reference manifest/context pack; it owns no canonical facts.
4. Keep Change Blueprints as temporary delta overlays; reconcile verified deltas into canonical knowledge and archive the change.
5. Replace `actions/` as the long-term organizing model:
   - service-like runtime units become components;
   - endpoints, DTOs, interfaces, and events become contracts;
   - pages/views become interface components connected to workflows and requirements.
6. Keep Markdown as the human-readable source format and add YAML front matter for machine-readable metadata.
7. Generate indexes and dashboards from canonical artifact metadata; do not manually maintain duplicate status tables.
8. Use lightweight IDs and links as an artifact graph; do not add a graph database.
9. Store exact source locations in a code map so every significant runtime file has an owner.
10. Separate deterministic validation from AI semantic review.
11. Split skills into atomic procedures and make workflows orchestration definitions.
12. Keep specialized agents optional. Roles define responsibility; one capable agent may perform several roles, while verification should be independent for high-risk changes.
13. Make the methodology core technology-independent; technology rules live in adapters and project profiles.
14. Migrate incrementally; do not rewrite v1.2 in one release-sized change.

## What v1.3 must preserve

- Change isolation: in-flight work does not silently rewrite canonical current state.
- Explicit approval for material product and architecture decisions.
- Vertical implementation units.
- Stable artifact IDs and traceability.
- Resumability across conversations and models.
- Initial-build and reverse-engineering entry points.
- Generic project knowledge separated from reusable engine procedure.
- Markdown readability and repository portability.

## What v1.3 must remove or reduce

- Manually synchronized copies of pack status.
- Flow logic duplicated between long flow files and skills.
- “Read all relevant files” as the context-building strategy.
- Verification reports that can declare PASS without evidence.
- Service-only modeling of runtime architecture.
- Change folders acting as permanent competing documentation.
- Central change-log edits from every parallel branch.
- Mandatory approval after every minor mechanical step.
- Framework assumptions in core methodology.

## Release-level definition of done

v1.3.0 is ready only when all of the following hold:

- A new project can initialize the canonical v1.3 knowledge tree.
- A v1.2 project can migrate without losing IDs or historical packs.
- The engine can create and validate structured artifact metadata.
- A change can be created, analyzed, planned, implemented, verified, reconciled, and archived.
- A context manifest and bounded context pack can be generated for one execution task.
- Significant changed source files must map to canonical components/contracts or an allowed classification.
- Deterministic validators reject invalid references, illegal transitions, stale generated indexes, unexplained changed files, and unevidenced verification.
- Skills contain procedure rather than project knowledge and satisfy the standard skill contract.
- Generated indexes remove the need for branches to manually edit one central log.
- The PollPulse example is migrated and passes all v1.3 validators.
- Package installation works for both supported agent targets and the package contains every required runtime asset.
- Documentation and examples describe v1.3 consistently.
