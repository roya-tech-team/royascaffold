# RoyaScaff v1.3 Validation and Reconciliation Plan

> Plan component 4 of 6. See [plan index](00-v1.3-plan-index.md), [target architecture](01-v1.3-target-architecture.md), and [workflow plan](03-v1.3-workflows-and-skills-plan.md).

## 1. Objective

Replace “the agent followed the Markdown” with enforceable contracts wherever correctness can be checked deterministically, while retaining focused AI/human review for semantic questions.

Validation has three levels:

```text
Schema validity
    ↓
Graph/lifecycle/plan-code consistency
    ↓
Semantic fitness review
```

A semantic reviewer cannot override a deterministic failure. A deterministic PASS does not prove the product design is correct.

## 2. Deterministic validation versus semantic review

### Deterministic validation

Use code for questions with objective answers:

- Is required metadata present and correctly typed?
- Are IDs unique and references resolvable?
- Is a lifecycle transition legal?
- Does a generated index match its sources?
- Did the implementation change files outside the task scope?
- Is every significant changed file classified in the code map?
- Were required commands executed successfully?
- Do declared contracts match machine-readable API/schema sources when an adapter supports it?
- Do expected tests exist and pass?
- Does the dependency graph violate declared architecture rules?
- Is the Context Pack based on the current source revision?
- Can the change delta apply cleanly to its baseline?

### AI semantic review

Use an AI/human for questions requiring judgment:

- Are requirements complete and unambiguous?
- Does the domain model express the right business meaning?
- Is the architecture appropriate rather than merely structurally valid?
- Are important failure cases missing?
- Are acceptance tests meaningful?
- Does the UI behavior satisfy the intended workflow?
- Is an architecture exception justified?
- Did impact analysis overlook a conceptual dependency not yet represented in the graph?

Semantic review outputs findings with severity, evidence, and disposition. It does not write a bare PASS checkbox.

## 3. Validator layers

### 3.1 Repository validator

Checks the whole `project/` knowledge repository:

- canonical directory and required entry files exist;
- artifact files satisfy their schemas;
- artifact IDs are unique;
- references and typed relation targets are valid;
- every canonical artifact has owner/lifecycle metadata;
- no active change is stored in archive and vice versa;
- generated indexes are fresh;
- no forbidden system-specific data appears in reusable engine core;
- no canonical document references an archived delta as current truth;
- deprecated/superseded artifacts link to successors or state why none exists.

### 3.2 Change validator

Checks one active change:

- metadata and current state are valid;
- baseline revision exists;
- state transition history is legal;
- affected artifact IDs resolve or are declared new;
- after-state delta paths mirror valid canonical destinations;
- impact includes every changed knowledge layer;
- compatibility, migration, security, rollout, and rollback are assessed according to risk;
- required approvals are present for the risk level;
- execution tasks cover every planned change artifact;
- dependencies are available for the requested transition.

### 3.3 Task validator

Checks one execution task:

- task has objective, owned artifacts/paths, acceptance subset, commands, outputs, and failure conditions;
- Context Manifest satisfies the skill context policy;
- Context Pack hashes match manifest sources;
- task changes remain inside allowed paths or record an escalation;
- created/modified files match the task result and code-map delta;
- required commands have evidence and successful exit status;
- task does not edit canonical knowledge.

### 3.4 Reconciliation validator

Checks the canonical update preview:

- change state is `verified`;
- target baseline includes required dependencies;
- delta applies without losing unrelated canonical content;
- new/modified artifact relations remain valid;
- removed artifacts are deprecated/superseded rather than silently deleted when history matters;
- implementation status is supported by evidence;
- code map covers verified file changes;
- generated indexes/system map can regenerate cleanly;
- archived change summary points to canonical after-state IDs.

## 5. Code map and orphan-file validation

### 5.1 Classification rule

Every significant runtime source file is one of:

- primary implementation of a component/action/contract;
- supporting implementation detail owned by a canonical artifact;
- configuration/wiring;
- migration;
- test/verification;
- generated output with named generator;
- excluded by a repository-level pattern and reason.

### 5.2 Blueprint-worthy threshold

A file needs its own `CMP-*` or `CTR-*` artifact if it:

- contains business rules or workflow orchestration;
- enforces security/authorization;
- owns persistence or transaction behavior;
- performs external I/O;
- exposes a public/cross-module interface;
- is a runtime entry point, job, consumer, or handler;
- is independently replaceable/testable behind a boundary;
- has meaningful cross-module reuse.

Small local helpers attach to an owner using `supports`; they do not create documentation bureaucracy.

### 5.3 Pack-time algorithm

```text
git/supplied change list
    ↓
normalize paths and apply generated/vendor exclusions
    ↓
compare with planned task paths
    ↓
resolve each path in pack code-map delta or canonical code map
    ↓
fail unexplained paths
    ↓
evaluate new files against blueprint-worthy threshold
    ↓
require component/contract record or explicit supporting owner
```

The CLI cannot perfectly determine semantic importance. It can deterministically require classification; AI review checks whether a file was incorrectly hidden as `supports`.

## 6. Plan-to-code consistency

### 6.1 Planned impact

Execution plans declare:

```yaml
artifacts:
  create: [CMP-ORDERS-API-006, CTR-ORDERS-API-012]
  modify: [WF-ORDERS-007, DATA-ORDERS-005]
  deprecate: []
paths:
  create:
    - apps/api/src/orders/approval.service.ts
  modify:
    - apps/api/src/orders/orders.controller.ts
  remove: []
tests:
  create:
    - apps/api/test/orders/approval.service.spec.ts
commands:
  - npm run typecheck
  - npm test -- orders/approval
```

Paths may use bounded globs when exact filenames cannot be known, but broad roots such as `src/**` require high-risk approval.

### 6.2 Deviation handling

When implementation differs from plan:

| Deviation | Required action |
|-----------|-----------------|
| Extra supporting file within same responsibility | Add to task result and code-map delta; revalidate |
| New component/contract | Stop task; update impact/design/plan; obtain required approval |
| Public contract change | Stop; compatibility and consumer impact review required |
| Architecture boundary violation | Fix implementation or approve an ADR/design revision |
| Requirement behavior change | Return to requirement/design state; never reconcile silently |
| Unplanned test/config update | Record reason and classify; approval based on risk |

The verifier never edits the plan to make implementation appear compliant.

## 7. Verification evidence model

```yaml
schema: royascaff/verification/v1
change: CHG-20260820-090000
source_revision: def456
deterministic:
  - id: schema
    result: pass
    tool: royascaff validate change
    exit_code: 0
    evidence: execution/evidence/schema.txt
  - id: tests
    result: pass
    command: npm test -- orders/approval
    exit_code: 0
    evidence: execution/evidence/tests.txt
semantic:
  - id: review-business
    result: pass_with_notes
    reviewer: reviewer-id
    findings: []
dispositions: []
overall: pass
```

Evidence rules:

- commands record command, working directory, timestamp, exit code, and output artifact;
- manual checks identify reviewer, method, and evidence such as screenshot or test record;
- skipped checks require reason, risk, and approving owner;
- evidence paths are repository-relative and secrets are redacted;
- verification becomes stale when relevant sources change after its recorded revision.

## 8. Architecture validation

The project architecture defines enforceable dependency rules:

```yaml
rules:
  - id: ARCH-LAYER-001
    from: controller
    may_depend_on: [application-service, contract]
    must_not_depend_on: [repository-adapter, vendor-sdk]
  - id: ARCH-FE-001
    from: page
    may_depend_on: [feature-service, store, shared-component]
    must_not_depend_on: [external-provider]
```

Adapters map source files/imports to component kinds where possible. Validation levels:

1. metadata dependency validation for all projects;
2. source import/dependency validation when an adapter supports the language/framework;
3. semantic architecture review for boundaries that static tools cannot infer.

Architecture exceptions require an accepted ADR or time-bounded waiver with owner and expiry.

## 9. Contract validation

Core checks:

- endpoint/message/UI boundary references valid `CTR-*` IDs;
- every interface/port has an implementation or `planned` status;
- consumers and implementations agree on contract version;
- breaking change flags compatibility/migration/consumer impact;
- DTO field mappings do not silently conflate domain, persistence, provider, and view models;
- sensitive fields declare classification and output constraints.

Adapter checks may compare canonical contracts with OpenAPI, GraphQL schema, protobuf, TypeScript types, C# interfaces, Java/Kotlin interfaces, JSON Schema, database migrations, or other project-native sources.

Canonical contract ownership is project-configurable: design-first projects may make Markdown normative; code/schema-first projects may declare a machine schema normative and generate/validate Markdown from it. The ownership choice must be explicit in `profile.md`.

## 10. Architecture decisions

ADR states:

```text
proposed → accepted → superseded
        ↘ rejected
accepted → deprecated
```

An ADR records:

- problem/context;
- decision drivers;
- considered alternatives;
- selected decision;
- positive/negative consequences;
- affected artifact IDs;
- transition/migration implications;
- owner/reviewers/date;
- superseding ADR when applicable.

Current architecture lives in `architecture/`. Rationale/history lives in `decisions/`. Accepted ADRs constrain current architecture but do not replace its readable after-state.

When an ADR is superseded, canonical architecture is updated through the change that implements the new decision. Historical ADRs remain discoverable but normal context includes only accepted decisions affecting selected artifacts.

## 11. Reconciliation transaction

Reconciliation is an explicit atomic operation:

```mermaid
sequenceDiagram
    participant R as Reconciler
    participant C as Verified Change
    participant K as Canonical Knowledge
    participant V as Validator
    participant I as Generated Indexes
    participant A as Archive

    R->>C: validate state, baseline, dependencies
    R->>K: create reconciliation preview
    R->>V: validate preview graph/status/code map
    V-->>R: PASS or failures
    alt PASS
        R->>K: apply after-state atomically
        R->>I: regenerate indexes/system map
        R->>V: validate final repository
        V-->>R: PASS
        R->>A: archive request, evidence, summary
        R->>C: mark reconciled
    else failure
        R-->>C: retain verified; no canonical mutation
    end
```

### Canonical update rules

- Apply complete after-state artifact sections, not appended chronological notes.
- Preserve unrelated sections byte-for-byte where practical.
- Reject stale baseline conflicts rather than choosing one delta automatically.
- Update `implementation_status` only with evidence.
- Regenerate derived indexes after canonical sources change.
- Reconciliation summary lists canonical paths/IDs updated and content hashes.

### Implementation deviation

If code behavior differs materially from the approved delta:

1. classify as implementation defect, plan defect, or newly discovered requirement;
2. return to the appropriate change state;
3. revise and reapprove material decisions;
4. reimplement/reverify;
5. reconcile only the final approved after-state.

### Abandoned changes

- state becomes `abandoned` with reason;
- canonical knowledge remains unchanged;
- generated active index removes it;
- archive keeps request, analysis, and decision history if useful;
- implementation branch cleanup remains a Git/team operation, not automatic destructive engine behavior.

## 12. Freshness and stale-plan detection

Record hashes/revisions for:

- change baseline;
- artifact sections used by impact/design;
- Context Manifest sources;
- execution plan inputs;
- verification source revision;
- reconciliation target.

Staleness policies:

| Event | Effect |
|-------|--------|
| Required context artifact changes | Context Pack becomes stale; rebuild before task |
| Affected contract changes | Pending task blocked until impact re-evaluated |
| Source changes after verification | Verification invalidated |
| Dependency reconciles with incompatible delta | Dependent change returns to analyzed/planned |
| Generated index source hash differs | Repository validation fails until regeneration |

## 13. Planned CLI surface

The CLI evolves carefully from installer to deterministic engine tooling:

| Command | Purpose | Mutating? |
|---------|---------|-----------|
| `royascaff init` | Install engine/skills and optionally initialize project knowledge | Yes, scoped |
| `royascaff validate [project|change|task|reconcile]` | Run schemas and invariants | No |
| `royascaff index` | Generate artifact/change/status indexes and system-map derived sections | Yes, generated files only |
| `royascaff context build --task <id>` | Resolve manifest and compile Context Pack | Yes, task context output only |
| `royascaff change create` | Create structured active change directory/metadata | Yes, new change only |
| `royascaff change transition <id> <state>` | Validate and record lifecycle transition | Yes, change metadata only |
| `royascaff reconcile <change>` | Preview/apply verified canonical delta | Yes, explicit command/gate |
| `royascaff migrate v1.2-to-v1.3` | Create migration workspace/report; never silently discard data | Yes, preview-first |

All mutating commands support `--dry-run` or preview where meaningful. Reconciliation and migration produce explicit file lists before applying.

## 14. Technology adapter contract

An adapter may provide:

- stack detection;
- source/test/generated path classification;
- component-kind inference;
- contract extraction/comparison;
- architecture/import checks;
- default build/type/lint/test commands;
- framework-specific templates and conventions.

Adapters cannot redefine core lifecycle, artifact identity, change isolation, or reconciliation semantics.

Initial delivery should include only adapters required to validate the existing example plus a generic adapter. A broad ecosystem belongs in later releases.

## 15. AI semantic review contract

Semantic review receives a dedicated Context Pack and outputs:

```yaml
schema: royascaff/semantic-review/v1
scope: CHG-20260820-090000
reviewed_artifacts: [REQ-ORDERS-014, WF-ORDERS-007, CTR-ORDERS-API-012]
findings:
  - id: FIND-001
    severity: blocking
    category: workflow
    artifact: WF-ORDERS-007
    evidence: Rejected-to-Draft transition has no authorization rule
    recommendation: Reference SEC-AUTHZ-003 and define allowed actor
overall: changes_required
```

Severity values are `blocking`, `high`, `medium`, `low`, and `note`. Every blocking/high finding needs a disposition: fixed, accepted risk with owner, duplicate, or not applicable with explanation.

## 16. Test strategy for the engine

### Unit tests

- metadata/schema parsing;
- ID and relation validation;
- state transitions;
- graph traversal and context policy;
- token/file budget selection;
- code-map matching and exclusions;
- index generation and freshness hashes;
- reconciliation delta/conflict handling.

### Fixture/integration tests

- valid small project;
- dangling relation;
- duplicate artifact ID;
- stale index;
- unplanned source file;
- illegal change transition;
- stale Context Pack;
- dependency unavailable locally;
- verified change reconciliation;
- reconciliation conflict and rollback;
- v1.2 migration fixture.

### End-to-end tests

- package/install into clean directory;
- initialize greenfield knowledge;
- create/design/plan/verify/reconcile a feature change;
- direct bug fix with regression evidence;
- reverse-engineer one example module;
- build context under budget;
- migrate PollPulse v1.2 and validate.

AI quality evaluation may use recorded scenarios, but deterministic release tests must not require a live model call.

## 17. Acceptance criteria

- A bare Markdown `PASS` cannot transition a change to verified.
- Deterministic failures block semantic acceptance and reconciliation.
- Changed runtime files cannot remain unexplained.
- Public contract deviations force impact/design review.
- Canonical changes are atomic and conflict-aware.
- Archived changes are excluded from current-truth validation/context by default.
- Indexes and Context Packs expose stale source revisions.
- Engine validation tests run without an AI model.
- Semantic findings are structured, evidenced, and dispositioned.
- Technology adapters extend discovery/validation without changing core methodology.
