## Decisions made without the owner

- **Events get IDs** (E0.3): `EVT-<CHG-ID>-<row>` and `EVT-PROJECT-<row>`, from the log row number. Logs are append-only, so the ID is stable; no new column in `log.md`.
- **Failed results are failures** (E0.3): `advance` refused is `GATE_REFUSED`; a failed `check`/`validate`/`roundtrip`/`migrate` dry run is `CHECK_FAILED`. The full result goes in a new optional `error.details` (minor change). `tasks`, `log` and `backups` now return `{ tasks }`, `{ events }`, `{ backups }` in `data` so they can grow.
- **Non-interactive mode** (E0.4): with `ROYASCAFF_NONINTERACTIVE=1` even a named person's `approve`/`measure` needs a signed token (`HUMAN_REQUIRED` otherwise), because nothing can be asked. Off by default; `ROYASCAFF_NO_TTY` keeps its old meaning.
- **Walkthrough test on Windows** (E0.0): it needs `sh` + `script` for a person's look; without them it skips at that step instead of failing.
- **Fingerprint by file content** (E1.2): the plan says "via git tree hashes"; the engine hashes the content of each covered file instead, so an edit that is not committed yet also makes evidence stale, and it works without git. Per-file hashes are cached for the life of the process.
- **verify writes one evidence record per run** (E1.2), holding every check's result and every acceptance line's result, not one record per check type. It uses the same event (`check.run`) as `check`, so the existing gates read it.
- **Which line a judge sees** (E1.3): a requirement with no acceptance lines has one line, `<ID>#1`, its title, so it can still be judged. Lines are keyed `<ID>#<n>` (n counts the acceptance lines from 1).
- **Judge identity** (E1.3): an AI judge must use `ai:<tool>:judge`; "built the tasks" means the `by` of the change's `task.started` and `task.done` events. The same tool in the judge role is allowed (a different identity), the same identity is not. Refusals use `GATE_REFUSED` (no new error code).
- **Foundation marking** (E1.4): a `- **Foundation:** SLC-…` field on the feature, not a column of the slice table, so existing tables keep their shape.
- **Schema file of the `adapter` command** (E2.1): the plan puts the manifest schema at `contract/schemas/adapter.schema.json`, but that name is also where the data schema of a command called `adapter` would go. The manifest keeps the planned name; the command's data is `adapter-result.schema.json` (`contract.schemaName(command)` maps it; documented in CONTRACT.md).
- **Dry run of a check** (E2.1): a declared check is "dry-run" by looking for its program (on the path, or the file for a path), or by running its own `dry` command; the real command is never started by `adapter test`.
- **Defaults for node and web-api** (E2.2): the plan names `transcript` for node and `demo` for web-api as defaults, so both manifests now declare a person's check (bars of 3 lines) and a person's look for feature changes at high risk. A project with only the `node` adapter therefore needs a "Usage bar" list in discovery topic 8 before `approve project`. The recorded run's commands are separated by ` ;; ` in one APP- field.
- **Inferred means "not an assumption"** (E3.1): `Basis: inferred` applies to any record except `ASM-` and `QST-`. Age is counted from `Inferred on:`; a record without a date only gets a warning asking for one. `confirm` has no signed-token form yet (the signed acts are fixed in plan 03 §6).
- **Layers a module needs** (E3.1): architecture always, plus the adapter's `layers.requires` and the layers of its `requiresDocs`. "Covered" is a mention of one of the module's components, or of the module's folder name, in the layer's pages or records.
- **Scan patterns** (E3.2): an item of `scan.patterns.<fact>` is a regular expression (first capture group is the fact) or `{ pattern, split }` for a list inside one match. Python support is a new engine adapter (`python`), not core code.
- **Stale evidence that was replaced** (E4.1): `ci`, `inventory` and the board list only stale evidence that no fresh evidence of the same kind for the same change has replaced; the old record stays in the file and stays stale.
- **Records from documents** (E3.3): `Source file:` is repository-relative; its records are history, so they are left out of the request coverage.
- **Guard condition** (E4.3): the plan says "folder equals the repo root"; here the engine is `engine/` inside the repo, so the guard fires when the engine's folder is the repo root or inside it, and not inside any `node_modules`.
- **Dogfood change kind** (E4.3): an AI cannot approve the project or a feature plan, so the real change is a `polish` change (no slice, low risk) affecting REQ-ENG-001. The project approval stays for the owner. The snapshot of the pinned tool is made with `core.autocrlf=false` (git archive otherwise gives CRLF templates on Windows, which breaks the parser on mixed line endings).
- **jti store** (E7a): the event logs (`jti <id>` in the note), not a separate file, so it travels with git and rebuilds from the repo. A token for several features is refused: one token = one feature, or `roadmap`. Hash for `roadmap` and `measure` is defined in CONTRACT.md section 8. A token with a missing default branch or list is `TOKEN_INVALID`.
