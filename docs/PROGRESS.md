## Decisions made without the owner

- **Events get IDs** (E0.3): `EVT-<CHG-ID>-<row>` and `EVT-PROJECT-<row>`, from the log row number. Logs are append-only, so the ID is stable; no new column in `log.md`.
- **Failed results are failures** (E0.3): `advance` refused is `GATE_REFUSED`; a failed `check`/`validate`/`roundtrip`/`migrate` dry run is `CHECK_FAILED`. The full result goes in a new optional `error.details` (minor change). `tasks`, `log` and `backups` now return `{ tasks }`, `{ events }`, `{ backups }` in `data` so they can grow.
- **Non-interactive mode** (E0.4): with `ROYASCAFF_NONINTERACTIVE=1` even a named person's `approve`/`measure` needs a signed token (`HUMAN_REQUIRED` otherwise), because nothing can be asked. Off by default; `ROYASCAFF_NO_TTY` keeps its old meaning.
- **Walkthrough test on Windows** (E0.0): it needs `sh` + `script` for a person's look; without them it skips at that step instead of failing.
- **Fingerprint by file content** (E1.2): the plan says "via git tree hashes"; the engine hashes the content of each covered file instead, so an edit that is not committed yet also makes evidence stale, and it works without git. Per-file hashes are cached for the life of the process.
- **verify writes one evidence record per run** (E1.2), holding every check's result and every acceptance line's result, not one record per check type. It uses the same event (`check.run`) as `check`, so the existing gates read it.
- **Which line a judge sees** (E1.3): a requirement with no acceptance lines has one line, `<ID>#1`, its title, so it can still be judged. Lines are keyed `<ID>#<n>` (n counts the acceptance lines from 1).
- **Judge identity** (E1.3): an AI judge must use `ai:<tool>:judge`; "built the tasks" means the `by` of the change's `task.started` and `task.done` events. The same tool in the judge role is allowed (a different identity), the same identity is not. Refusals use `GATE_REFUSED` (no new error code).
- **Foundation marking** (E1.4): a `- **Foundation:** SLC-…` field on the feature, not a column of the slice table, so existing tables keep their shape.
- **Schema file of the `adapter` command** (E2.1): the plan puts the manifest schema at `contract/schemas/adapter.schema.json`, but that name is also where the data schema of a command called `adapter` would go. The manifest keeps the planned name; the command's data is `adapter-result.schema.json` (`contract.schemaName(command)` maps it; documented in CONTRACT.md).
- **Dry run of a check** (E2.1): a declared check is "dry-run" by looking for its program (on the path, or the file for a path), or by running its own `dry` command; the real command is never started by `adapter test`.
- **Defaults for node and web-api** (E2.2): the plan names `transcript` for node and `demo` for web-api as defaults, so both manifests now declare a person's check (bars of 3 lines) and a person's look for feature changes at high risk. A project with only the `node` adapter therefore needs a "Usage bar" list in discovery topic 8 before `approve project`. The recorded run's commands are separated by ` ;; ` in one APP- field.
- **Inferred means "not an assumption"** (E3.1): `Basis: inferred` applies to any record except `ASM-` and `QST-`. Age is counted from `Inferred on:`; a record without a date only gets a warning asking for one. `confirm` has no signed-token form yet (the signed acts are fixed in plan 03 §6).
- **Layers a module needs** (E3.1): architecture always, plus the adapter's `layers.requires` and the layers of its `requiresDocs`. "Covered" is a mention of one of the module's components, or of the module's folder name, in the layer's pages or records.
- **Scan patterns** (E3.2): an item of `scan.patterns.<fact>` is a regular expression (first capture group is the fact) or `{ pattern, split }` for a list inside one match. Python support is a new engine adapter (`python`), not core code.
- **Stale evidence that was replaced** (E4.1): `ci`, `inventory` and the board list only stale evidence that no fresh evidence of the same kind for the same change has replaced; the old record stays in the file and stays stale.
- **Records from documents** (E3.3): `Source file:` is repository-relative; its records are history, so they are left out of the request coverage.
- **Guard condition** (E4.3): the plan says "folder equals the repo root"; here the engine is `engine/` inside the repo, so the guard fires when the engine's folder is the repo root or inside it, and not inside any `node_modules`.
- **Dogfood change kind** (E4.3): an AI cannot approve the project or a feature plan, so the real change is a `polish` change (no slice, low risk) affecting REQ-ENG-001. The project approval stays for the owner. The snapshot of the pinned tool is made with `core.autocrlf=false` (git archive otherwise gives CRLF templates on Windows, which breaks the parser on mixed line endings).
- **jti store** (E7a): the event logs (`jti <id>` in the note), not a separate file, so it travels with git and rebuilds from the repo. A token for several features is refused: one token = one feature, or `roadmap`. Hash for `roadmap` and `measure` is defined in CONTRACT.md section 8. A token with a missing default branch or list is `TOKEN_INVALID`.

### 1.6 (E6.1 to E6.5)

- **Contract 1.1 from E6.1** (the plan's rule: additions are minor). Schemas new in 1.6 carry `$id` `…/contract/1.1/…`; the older ones keep `1.0` (the version they were introduced in). `errors.json` is written from the table (`writeErrorsFile`); no error code was added, so the schema enum is unchanged; `measure`'s `result` enum became "met, not-met, stop or keep <variant>".
- **A record's version is derived** (E6.1): 1 plus the deltas of `evolve` changes at status approved or later, not reverted. Nothing is typed, so it rebuilds from the repo. It is in the evidence fingerprint of every change that delivers or affects the record (only when above 1), so old evidence goes stale when the design is approved, not when the change closes. `status` and `export` show `version` only when above 1.
- **New change kinds** `evolve` and `rollback`; `open --kind evolve|rollback` is refused with a pointer to `change` and `rollback`. The delta block is `## Delta <ID> (v1 → v2)` with `Before:`, `After:`, `Why:`; the list of what depended on the old wording is the table `## Affected by the delta` (Item, Kind, Why, Handling). A contract delta is breaking when a backticked word of Before is missing in After, or `Removes:` or `Breaking: yes` says so.
- **Baselines** (E6.2): the plan says "uses the contract's export schema" and "every REL- by default". The baseline reuses the shapes of `export` (links, status, evidence) and adds each record's version, hash and wording, under its own format name and schema (`baseline.schema.json`); it holds no change or task (their logs are the history). "By default" is: `new record release … --includes CHG-…` writes it at once; otherwise `royascaff release REL-…`. It is frozen: never rewritten.
- **`diff` causes** (E6.2): the evolve change that holds the delta; for added and removed records, the changes that deliver, affect or name the record, limited to the changes the later release adds (for `now`: those not in the earlier release). **`history`** version 1 comes from git (`git log -S "<ID> ·"`), so it is empty without git.
- **Flags and the board** (E6.3): the board has no wall clock, so it measures "past removal" against the date of the last recorded event; `validate` and `inventory` use today (`ROYASCAFF_TODAY` fixes it for tests). A flag naming a release is due once that release record exists. `Remove by` is not checked as a mention (it may name a release not made yet). The experiment metric accepts a name without a dot (`signup_rate`, the plan's own example); an NFR measure still needs one.
- **Experiments** (E6.3): a person decides (`measure EXP-…`); one removal slice per variant that lost, on the experiment's `Feature` (none when it has none). Only `keep <variant>` or `stop` are decisions.
- **Rollback** (E6.3): the default risk is medium (a person approves the design). A reverted change counts as reverted from the moment the rollback's design is approved (like a delta), so the gate can check that the records are back. The commits listed are those touching code outside `project/` (a commit that only touches the project folder is bookkeeping, and git cannot tell the engine's own board rewrites from a person's edit of a record); records go back through the Restore table. The option to name the baseline is `--to REL-…` (`--baseline` is a boolean flag of `release`).
- **Deprecation** (E6.3): any identity may deprecate (it schedules removal, it approves nothing); the event `record.deprecated` names who. Requirements and components only.
- **Checkpoints** (E6.4): 60 000 tokens of source (bytes / 4) per checkpoint by default, against a 200 000-token window; the target (at most 60% of the window) is reported, not enforced. `adopt --plan` opens `knowledge` changes with `module:` in the front matter and no tasks; progress is derived from code ownership.
- **Scan cache** (E6.4): version 2 adds `files` (size, modification time, when seen). A file is trusted only when it is more than 2 s older than the scan (git's racy rule), so an edit within the same moment is still read. `data.cache` keeps its two numbers; `data.reads` is new.
- **Migration** (E6.5): opt-in (`--from 1.5`), because a 1.4/1.5 project already works on 1.6. The profile format number stays `1.4` for new projects (`init` templates, and tests rely on it); the 1.6 engine reads 1.4, 1.5 and 1.6. The apply does not run `index` (it would rewrite the board and summary blocks, which are not in the manifest and could not be rolled back byte for byte); the next command refreshes the board.
- **Skill budget** (E6.3): to keep SKILL.md at 400 tokens, "Arabic or English" left its description (the rule "Reply in the person's language" stays) and the change/rollback/deprecate guidance lives in `cards/fix.md`.
### 1.7 (E7b.1 to E7b.4)

- **MCP without a dependency** (E7b.1): JSON-RPC over stdio (newline-delimited) and HTTP is small, so the server is plain Node (`http`, `crypto`, `readline`). It speaks the initialization-based protocol versions 2024-11-05 to 2025-11-25 and also answers requests that arrive without `initialize` (the 2026-07-28 revision is stateless and has no `initialize`; only the methods used here were checked, not the whole revision).
- **A tool is the CLI** (E7b.1): a tool call runs the CLI command as a child process with `--json` and `ROYASCAFF_NONINTERACTIVE=1`, and hands back its envelope unchanged. This costs one process per call (about 0.2 s) and makes the CLI and MCP results identical by construction (C5). Bad input is an `INVALID_INPUT` envelope with `isError`, not a JSON-RPC error; an unknown tool is a JSON-RPC error.
- **MCP agents are never people** (E7b.1): every acting tool takes an optional `agent` (default `mcp`) and the engine records `ai:<agent>`. A tool whose ID or title starts with `-` is refused so it cannot be read as an option.
- **`request-approval`** (E7b.1) is a new CLI command (the plan names only the tool). Event `approval.requested` in the change's log, or the project log; the note is JSON with the act. Nothing reads it yet: Studio does.
- **HTTP details** (E7b.1): listens on `127.0.0.1` unless a host is given; a token shorter than 16 characters is refused; a random token is printed on stderr when none is given; `Origin` must be localhost when present; a client that sends no session header shares one anonymous session; the event stream is `GET /mcp` with the session header.
- **install** (E7b.1): `install` (both tools by default) always registers the server; there is no option to skip it. The entry uses the same CLI as the skill (`npx royascaff mcp` when installed in `node_modules`, else the runtime and the engine's `bin` path).
- **Claims** (E7b.2): the log is the only store (`claim.acquired` / `claim.released` events, JSON note). Overlap compares the folders before the first wildcard (can raise a false alarm, never misses). Default lease 30 minutes, at most 24 hours, fractions allowed. A claim by the holder renews. `ROYASCAFF_NOW` moves the claim clock (tests). `task start` and `task done` check the holder; `task block` does not.
- **`events --follow`** (E7b.2) polls the log files every 250 ms (works on every platform) and prints event objects, not envelopes. With `--since` it prints the backlog first.
- **One commit for E7b.1 and E7b.2** because their changes share the CLI, the contract and the goldens.
- **Runner** (E7b.3): the queue protocol (long-poll GET, accept, events, result) is mine, since the plan names only the job, the loop and the event kinds; documented in `RUNNER-PROTOCOL.md`. The runner pins the engine by comparing the job's `engine_version` with the engine it was given (`--engine`); installing a version is a real runner's job. It stops the agent when turns pass `max_turns` or the cost passes the budget (reaching the limit exactly is allowed). It pushes work after `finished`, `max_turns` and `budget`, not after a failure or a cancel. The agent protocol (JSON lines `tool_use`, `cost`, `log`) belongs to the reference runner.
- **Skill budget** (E7b.4): SKILL.md stays under 400 tokens by shortening other lines; the "hand-made commits" hint left step 2.
- **C1 without Claude Code** (E7b.4): the two clients are written by hand (stdio and HTTP). "No repository scanning" is measured two ways: the client's own call log and the server's log (`ROYASCAFF_MCP_LOG`) must be equal and contain only the 14 tools and `royascaff://` reads. The agent still writes its code to disk itself.
- **Test cost**: the full suite takes 5 to 8 minutes; `e63` (rollback with git) and `e64` (200 000 generated lines) are the heavy files. The B4 validation script was run from outside the repository (not committed): it needs three full-suite runs (about 20 minutes).
